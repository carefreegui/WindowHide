## 隐藏为什么任务栏会消失?

两个动作叠加:`ShowWindow(SW_HIDE)` 让窗口不可见,
再给窗口加 `WS_EX_TOOLWINDOW` 扩展样式——带该样式的顶层窗口不出现在任务栏和
Alt+Tab 中。恢复时两者都会还原。即使目标程序自己调 `ShowWindow(SW_SHOW)`,
工具窗口样式也能保证它不会回到任务栏(看门狗每秒复查,可关)。

<a id="s2"></a>

## 全屏游戏藏不掉?独占全屏根本不看窗口可见性

全屏游戏按隐藏,
声音静了、画面还在屏幕上。原因:独占全屏的游戏由 D3D/DXGI 直接把画面翻转
输出到显示器,`WS_VISIBLE` 与最终画面是两条路 —— 把窗口 `SW_HIDE` 掉,
窗口"看不见了",游戏却照旧渲染。
*修复:全屏窗口(无标题栏 + 铺满所在显示器)可以走 **先最小化、再隐藏**:
`WM_SYSCOMMAND/SC_MINIMIZE` *+* `ShowWindowAsync(SW_MINIMIZE)`,等它掉出
独占全屏后再 `SW_HIDE`。判据改成 `is_offscreen`(隐藏**或**最小化),
否则全屏游戏最小化后 `IsWindowVisible` 仍是 True,会被误记成"失败"。*
*判定必须排除三类"铺满屏幕但不是游戏"的窗口,否则会误走最小化路径:
带 `WS_CAPTION` 的最大化窗口、`WS_EX_NOACTIVATE/LAYERED/NOREDIRECTIONBITMAP`
的覆盖层(实测有 `Windows 输入体验`、`NVIDIA GeForce Overlay`)、
`WS_DISABLED` 的桌面 `Progman`。附带:桌面/任务栏窗口不再出现在列表里
(`win32.is_shell_window`),断了"一键把桌面藏了"的第二次机会。*
*另外隐藏失败现在会**说出来**(托盘气泡 + 状态栏 + 日志),以前是静默
假装成功 —— 静默失败比失败本身更坑。*

<a id="s3"></a>

## 但这招有代价,所以默认关掉

实测永劫无间:最小化之后它主线程再也不处理
消息(`IsHungAppWindow` 为真),此后 `ShowWindowAsync` 的请求永远堆在无人
处理的队列里 —— **游戏自己回不来**,窗口又是 `WS_POPUP`、没有任务栏按钮、
不在 Alt+Tab 里,用户没有任何入口点回去。所以:

- 默认只做安全的那一半(`SW_HIDE` + 工具窗样式),藏不住就报"没藏掉";
- 设置里勾「强制隐藏独占全屏游戏」才走最小化路径,并明确标注风险;
- 走最小化路径时若"最小化成功、隐藏失败",立刻 `_undo_hide` 撤回原样,
  绝不留半残状态。

<a id="s3b"></a>

## 后来的办法:不碰"可见",只碰"可见区域"

既然引擎对 `WS_VISIBLE` 这么敏感,那就别动它。`SetWindowRgn(hwnd,
CreateRectRgn(0, 0, 0, 0), TRUE)` 把窗口的**可见区域**设成空 —— 位置、大小、
`WS_VISIBLE`、扩展样式全都不变,窗口"还在那儿正常显示",只是没有一个像素
落在可见区域里。区域由窗口管理器裁剪,应用拦不住;恢复就是 `SetWindowRgn(hwnd,
NULL, TRUE)` 把区域清掉。

这条路对全屏游戏有效(实测永劫无间全屏、异环全屏都能藏、能恢复),原因是它
绕开了两个死胡同:

- 全屏窗口会**钉死自己的位置**(在 `WM_WINDOWPOSCHANGING` 里改回去),所以
  "挪出屏幕"对全屏无效 —— 实测窗口矩形全程一次没变;
- 而 `SW_HIDE` 会被引擎当成"窗口没了",渲染循环和消息泵一起停掉,CPU 掉到 0、
  内存还占着、标题变"(无响应)",之后连改样式都超时,窗口再也救不回来。

顺带记一条死路:窗口化游戏能用 `DwmSetWindowAttribute(DWMWA_CLOAK)` 藏,
但对**别的进程**的窗口一律返回 `E_ACCESSDENIED` / `E_HANDLE` —— 那个 API
只对自己进程的窗口有效,别浪费时间。

代价与边界:自己原本就设过区域的窗口(异形/圆角窗口)不能碰,原样还原不了;
真·独占全屏(D3D 直接翻转输出、完全不经过窗口管理器)改区域也不生效,这时
工具会报失败并还原,建议用户改成「无边框窗口化」。

<a id="s4"></a>

## 目标无响应时,任何窗口操作都可能把调用方一起卡死

现象:隐藏一个卡死的
全屏游戏,工具界面直接变成"未响应",只能强杀进程。根因是主线程上做了跨进程
**同步**窗口调用(`SetWindowLongPtr` / `SetWindowPlacement` / 同步
`SetWindowPos` 都要等目标线程处理),目标不处理就永远等下去。
*三道护栏:① **隐藏/恢复全部放工作线程**,主线程只发信号、画界面;② 动手前
用 `IsHungAppWindow`(Windows 自己的"未响应"判定)检查,发现 hung 就**完全
不碰**并说明原因;③ 能异步的一律异步 —— `ShowWindowAsync`、
`SetWindowPos(... | SWP_ASYNCWINDOWPOS)` 投递到对方队列就返回。*
*顺带发现:`WM_NULL` + `SendMessageTimeout` **不能**用来判断目标是否响应
(不对消息循环的窗口照样返回成功),必须用 `IsHungAppWindow`。*

<a id="s5"></a>

## 托盘图标为什么能删掉?

托盘图标由 `Shell_NotifyIcon(NIM_DELETE)` 删除,
该 API 内部向 explorer 的托盘工具栏发消息,不校验发送方进程,因此可以跨进程删除。
uID 未知时遍历 0..64 试探。恢复时向目标进程广播 `TaskbarCreated` 消息,
应用会按微软文档推荐的做法重新注册自己的图标。
*已知限制:以 GUID 方式注册图标的程序(部分新版 Electron/国产软件)无法从外部
获知 GUID,其托盘图标会保留,但窗口本身照样隐藏。*

## 静音

用的是系统音量合成器同一套接口(Core Audio `ISimpleAudioVolume`),
纯 ctypes 实现,只影响目标程序的音频会话。
*踩坑记录:`CLSID_MMDeviceEnumerator` 是 `{BCDE0395-E52F-467C-8E3D-C4579291692E}`,
第三段是 **467C**(见 `mmdeviceapi.h`),误记成 467E 会让 `CoCreateInstance`
返回 `REGDB_E_CLASSNOTREG`;另外 `IAudioSessionManager2::GetSessionEnumerator`
在 vtable 索引 5(前面有两个方法),`IAudioSessionControl2::GetProcessId`
在索引 14(前面有 11 个方法)。*

<a id="s7"></a>

## 浏览器静不了音?因为音频不在主进程放

现象:浏览器能隐藏但静不了音,
游戏却能静。原因:Chromium 系(Edge/Chrome)的声音由 **audio service 子进程**
播放(实测 Edge 主 pid 零会话,2 个会话全在子进程上),按主窗口 pid 找会话
当然静不了;游戏是主进程直接放音频,所以旧逻辑对游戏有效。
*修复:`set_process_mute` / `is_process_muted` 的目标从单个 pid 扩展为
**pid + 全部子孙进程**(`win32.process_descendants`,toolhelp 快照建父子表
再 BFS)。用进程树而非进程名匹配,不会误伤同名的其它浏览器实例。
回归测试 `audio_tree_test.py` 用"父进程无会话、子进程播音"确定性复现。*

<a id="s8"></a>

## 窗口枚举必须防挂起

`GetWindowTextW` / `WM_GETICON` 都是跨线程
`SendMessage`,遇到"无响应"进程的窗口会**无限期阻塞调用方** —— 曾导致
点击隐藏后整个工具卡死(栈停在 `get_window_text`)。现在统一改用
`SendMessageTimeoutW`(`SMTO_ABORTIFHUNG`,100ms 超时),挂起窗口的标题
降级为空串,不影响其它窗口;枚举时也先按 pid 过滤再取详情,
避免对全系统窗口逐个发消息。

<a id="s9"></a>

## 热键

独立线程建消息窗口 + `RegisterHotKey`,`MOD_NOREPEAT` 防连发;收到 `WM_HOTKEY` 后通过 Qt 信号转主线程执行,响应延迟在毫秒级。
*踩坑记录(实测"改设置后快捷键没反应"):窗口类名必须按线程唯一化 ——
同进程内第二次 `RegisterClassW` 同名类必然失败,旧线程还没退出完时新线程
起不来,旧热键已注销、新热键没注册,热键整个静默死掉。现在类名带线程序号,
且线程起不来/注册失败必须写日志 + 发信号(托盘气泡提示),绝不允许静默;
`RegisterHotKey` 另带 6 次重试兜底旧线程退出超时的竞态。*

### 纯 Shift 组合:从「拒绝」改成「旁听」

第一版是**拒绝**。理由很硬:`RegisterHotKey` 一旦接管 `Shift+Enter`,聊天换行、
`Shift+字母` 大写就全废了 —— 用户当时的描述是"键盘像坏了一样"。所以录入时直接
拦下,启动时还会把配置里已经存着的危险值自愈成默认键。

但用户后来把话说清楚:「Shift+Enter 其实特别好操作,你反而多了三个键之后没那么
顺畅,稍微占用一点也可以,同时触发也可以,提醒一下就行」。拦着等于替他做决定,
而且"自愈"会让他每次启动都发现自己的键变了。

技术上要满足"两个都触发"只有一条路:**不用 `RegisterHotKey`,改用
`WH_KEYBOARD_LL` 旁听** —— 看到就发信号,然后无条件 `CallNextHookEx` 放行。
原程序照常收到那个键,本工具也同时执行动作。三条约束:

- **修饰键要归一化**:钩子报的是 `VK_LSHIFT(0xA0)` 而不是 `VK_SHIFT(0x10)`,
  不归一化就永远匹配不上配置里的 `MOD_SHIFT`;
- **按住不放不能连发**:钩子会连续给 `WM_KEYDOWN`,用一张 `fired` 表挡住重复;
- **任何键抬起都清空 `fired`**,修饰键状态一变也清空 —— 否则"按住 Shift →
  松开 Shift → 再按 Enter"会把残留状态当成还按着 Shift。

这个钩子挂在全系统的键盘输入通路上,所以回调里只做整数比较和一次字典查找,
整段 `try/except`、异常计数到阈值自我停用。侧键和旁听功能废掉都可以接受,
拖累整台机器的输入不行。

代价说在明处:这类键在别处也会顺手触发一次。所以设置页会提示"配不常用的键
更舒服(`Shift+F8` 比 `Shift+Enter` 稳)",但**不拦**。

<a id="s10"></a>

## 隐藏状态持久化

隐藏记录(pid + hwnd + 原样式)落在
`%APPDATA%\WindowHide\hidden_state.json`,每次变更即写盘;启动时逐条校验
(进程存活 / IsWindow / pid 匹配 / 当前不可见 / 带 TOOLWINDOW 样式),
不合格的丢弃。否则工具重启后"还藏着的窗口"会变成孤儿 —— 界面不显示、
热键恢复找不到目标,只能手动重启目标程序。

<a id="s11"></a>

## `GetForegroundWindow` 在托盘菜单场景是个陷阱

现象:从托盘菜单点
"隐藏当前前台窗口",一键把**桌面、任务栏连同所有资源管理器窗口**全藏了。
原因:菜单弹出的瞬间前台窗口变成 explorer 的 Progman / Shell_TrayWnd,
按 pid 藏进程 = 藏整个 explorer。同理,在主界面点按钮时前台是工具自己,
会把自个儿藏掉。*结论:"隐藏当前前台窗口"这个交互从托盘/主界面/快捷键
全部撤掉,改为用户真正想要的「隐藏本工具(收进托盘)」;core 的
`hide_foreground` 保留但加了桌面/任务栏/自身三重保护备用。*

<a id="s12"></a>

## 目标程序以管理员权限运行时,我们能做的极其有限(UIPI)

现象:永劫无间
(全屏,管理员权限运行)点隐藏后"只最小化到桌面、还点不回来"。
排查结论:`OpenProcess(PROCESS_VM_READ)` 对它返回 **错误 5**,
而工具自身是普通权限 —— UIPI 把 `SetWindowLongPtrW`(加 TOOLWINDOW)、
`SetWindowPlacement`、`SetForegroundWindow` **全部静默拦掉**,只有
`ShowWindowAsync(SW_MINIMIZE)` 生效。更糟的是游戏窗口是 `WS_POPUP` 且没有
`WS_EX_APPWINDOW`:最小化之后**没有任务栏按钮、也不在 Alt+Tab 里**,
用户根本没有入口点回去。
*修复三层:*
*① **动手前先问权限**(`win32.process_is_higher_integrity`,用
`PROCESS_VM_READ` 能不能拿到判断)—— 权限不够就**完全不碰**,弹气泡说明
"请以管理员身份重启";*
*② **全有或全无**:全屏窗口"最小化成功、隐藏失败"时必须**回滚**
(`_undo_hide` 拉回原位),绝不能把窗口丢在"最小化且点不回来"的死角;*
*③ 托盘菜单加「**以管理员身份重启**」(`ShellExecuteW runas`,新进程带
`--elevated` 跳过单实例检查,旧进程 `os._exit` 直接退出以让出互斥体)。*
*恢复路径也一起加固:`SetWindowPlacement` 直接改窗口状态(游戏对
`ShowWindow(SW_SHOWNORMAL)` 可能完全没反应),抢前台改用
`AttachThreadInput` 那条路,且全程只用异步 API —— 同步 `ShowWindow`
跨进程要等目标线程,游戏主循环一卡就把工具的 UI 冻住。*

<a id="s13"></a>

## 场景是什么、为什么这么设计

单纯"记住一批窗口"解决不了真问题:换场合时
用户要的是**切换**,不是重新勾一遍。所以场景的定义是"藏这批 + 放掉别的场景藏的
那批",而**手动勾选藏的窗口永远不动** —— 那是用户自己的临时决定,不该被场景
覆盖。切换语义写死在这三条规则里,没有隐藏开关。

<a id="s14"></a>

## 隐藏的单位是窗口,不是进程 —— 浏览器多开为什么会被一锅端

用户报的现象:Edge 开了五个窗口,勾其中一个按隐藏,结果**五个全没了**。

根因不在 Win32,而在控制器:`hide_hwnds()` 拿到 hwnd 列表后**折叠成了 pid**,
再交给 `hide_pids()` 去枚举"这个进程的所有窗口" —— 同进程的兄弟窗口自然被
一起藏了。Chromium 系(Chrome / Edge / Electron)只要用同一个
`--user-data-dir`,多开出来的窗口就同属一个进程,所以必然踩中。

先验证了 Win32 侧的边界,结论很干脆:**隐藏本来就是窗口级的**。
同一个进程里两个顶层窗口,`ShowWindow(SW_HIDE)` + `WS_EX_TOOLWINDOW` 只作用
在目标 HWND 上,兄弟窗口照常可见、照常能交互,进程也不受影响;恢复也一样。
所以问题纯在数据结构上 —— `HiddenProcess` 按 pid 存没问题(它本来就带
`records[hwnd]`),问题只是"藏的时候没看这份记录"。

现在的语义分成两层,别再混:

| 入口 | 粒度 | 谁在用 |
|---|---|---|
| `hide_hwnds(hwnds)` | **窗口级**,只动列表里的 HWND | 手动勾选、双击行、快捷键切换 |
| `hide_pids(pids)` | 进程级,枚举整个进程 | 场景切换、规则持续生效 |

配套还有三条约束,都是"整进程级动作不能对局部隐藏生效"的推论:

1. **只藏了一部分窗口时不删托盘图标、不静音**。`Shell_NotifyIcon(NIM_DELETE)`
   和音量合成器都是按进程(甚至进程树)生效的,对半个程序做这两件事,会把
   用户留着在用的那个窗口的托盘图标和声音一起干掉。`HiddenProcess.partial`
   这个标记就是为此存在,并且要落盘 —— 否则重启后看门狗的"补刀"会把用户
   特意留着的那几个窗口一起藏了。
2. **`partial` 时禁用"先最小化再隐藏"**。最小化是整进程的动作(见 s3),同
   进程还有窗口在屏幕上时坚决不用,连全屏窗口也退回到纯 `SW_HIDE`。
3. **看门狗补刀只补我们自己藏过的窗口**(`hp.partial` 时按 `hp.records`
   过滤)。否则"同程序多开只藏一个"会变成"三秒后全都藏了"。

另外一个容易漏的点:`_pending` 是**进程级**的在途意图表,同程序多开时不够用
(藏了 A 再点 B,进程级会误判成"B 也藏过"),所以窗口级操作单开一张
`_pending_hwnd`。这类"异步落地前的真空期"判断一旦用错粒度,表现就是
"点了没反应"—— 和当初 pid 版本踩的坑一模一样。

<a id="s15"></a>

## 声音只能按程序关,不能按窗口关

用户想让"浏览器 A 窗口在放歌,我只藏 A,别的窗口不受影响" —— 视觉上可以
(见 s14),声音上**不行**。系统音量合成器(Core Audio)的会话是挂在
**进程**上的,一个程序只有一路音量;同一个 Chromium 进程里开五个窗口,
`IAudioSessionManager2` 里也只有一条会话。想"这个窗口静音、那个继续响"
在 API 层面就没有对应的东西(除非注入进程自己改混音,那是另一个性质的工具)。

实测(同一台机器,Edge 开两个窗口各放一路 440Hz/660Hz 正弦):
系统里只有 **两条** 会话,而且两条分别属于**两个浏览器进程**(各自一条)。
换句话说,一个浏览器进程不管开几个窗口,音量合成器里只有一路 —— 想按窗口
分,连"多路会话"这个前提都不存在。

所以策略只能定成程序级,分成两层:

1. **默认按设置来**(设置 → 行为 →「隐藏时同时静音」)。局部隐藏也照样
   静音 —— 这是用户实测反馈的期望:"藏了就别响"。代价是同程序没被隐藏的
   窗口也会一起没声,这一点必须写进提示里,不能装作没有。
2. **按程序豁免**:主界面「声音」列勾上 = 这个程序藏了也继续响。存在
   `config.keep_audio_processes`(进程名小写)。勾选时如果程序正在隐藏中,
   立刻 `set_process_mute(False)` 生效 —— 否则用户得"恢复再藏一遍",
   而恢复会把窗口弹到前台,正好是他在躲的东西。

另一半是**恢复时的方向性**:既然静音是整进程级的,放出**任何一个**窗口就
该把声音还回来(`_unmute`),不能等"整个进程都放回来"。否则用户把正在听
的那个窗口点回来,发现是哑的。

托盘图标则相反:只在整个程序藏干净时才删。图标不像音量那样"能自己恢复",
半藏状态下删掉,用户看到的是"浏览器还在、托盘图标没了"。

<a id="s16"></a>

## 勾选状态不能从界面行反推

用户实测:"多按几次隐藏快捷键,勾选自己就变成没勾了,再按就认不出来"。

根因是**异步隐藏与界面刷新的赛跑**:`ShowWindowAsync(SW_HIDE)` 投递出去后,
窗口很快就"不可见"了,但工作线程还要走完"等落地 → 写记录 → 存盘"才把
hwnd 记进 `_hidden`。这中间的一小段里窗口:

- `IsWindowVisible` 已经是 False → 被 `refresh()` 的"可见窗口"过滤掉;
- 还不在 `hidden_hwnds()` 里 → 也不满足"被我们隐藏"的条件。

于是这一帧的列表里没有它,而旧代码每次重建表格都 `self._checked = set()`
再按现有行重新收集 —— 行没了,勾选就被静默抹掉。概率性出现,取决于那 1.5 秒
定时器是不是正好落在空窗期里;按得越勤,踩中的机会越多。

修法三条:
1. **`_checked` 是唯一真相,不再按行重建**。只清理真的没了的窗口
   (`IsWindow(hwnd) == False`),"暂时不在列表里"不算消失
   —— 被搜索框过滤掉的情况顺带也修好了。
2. `checked_hwnds()` 返回 **行内勾选 ∪ `_checked`**,所以哪怕这一帧没有行,
   `隐藏勾选`/快捷键依然认得出它。
3. `refresh()` 把 `pending_hwnds()`(在途意图)也算进"要保留的行",
   让行根本不闪。两层保险:一层防"行消失",一层防"行没了但状态还在"。

回归:`tests/checkbox_test.py` 的 `[5.6]` 直接构造"这一帧没有该窗口"的列表,
`[5.7]` 真跑一次异步隐藏并连刷 30 帧,断言勾选一次都没丢。

<a id="s17"></a>

## 类型是程序的属性,不是窗口此刻的状态

用户报:"类型标着**游戏**的窗口,一点隐藏,类型就变成**其他**了,别的类型不会。"

原因是分类器每帧重算,而最后那条兜底规则长这样:

```python
if not win.visible or not win.title:   # ← 隐藏之后 visible 就是 False
    return False
```

可见性被当成了"像不像游戏"的判据,于是**藏起来的游戏当场不算游戏**。而这条
规则恰恰是唯一能给"进程名认不出来"的游戏(Unity/Unreal 打包的国产端游基本
都这样)定性的规则 —— 所以只有游戏会中招,浏览器(靠进程名精确匹配)完全不受
影响,和用户观察到的现象一模一样。

修法分两步,只有第一步是不够的:

1. **结果按 `(hwnd, 进程名)` 粘住**。类型是程序的性质,认出来一次就不再改口。
   这比"把所有规则都改成不依赖可见性"安全 —— 后者会引入新的误判(UWP 的
   `CoreWindow` 也是无边框大字窗),而缓存不需要放宽任何判据。
2. **加一条不看可见性的引擎特征**:窗口类名含 `UnityWndClass` /
   `UnrealWindow` / `SDL_app` 就判游戏。这样"工具启动时游戏已经被藏了"也认得
   出来(那种情况下缓存里是空的)。

顺带把另外两个识别问题一起修了,它们其实是同一个病:**靠进程名穷举**。

- **微信 4.x 把 `WeChat.exe` 改成了 `Weixin.exe`**,企业微信是 `WXWork.exe`,
  小程序容器是 `WeChatAppEx.exe` —— 名单里只有 `wechat.exe`,于是新版微信
  全被判成「其他」。
- **QQ 系共用 `qq` 前缀**,`QQMusic` / `QQBrowser` / `QQGame` 谁先命中谁说了算,
  所以前缀规则必须**按"最具体优先"排序**,`qq` 兜底放最后。

穷举永远会漏,所以补了第四层兜底:**读 exe 的「文件说明」**(资源管理器 属性
→ 详细信息 那一栏),按关键词归类。它是给人看的字符串,同厂商基本一致,
微信是 "Weixin"、网易云音乐是 "网易云音乐"。纯读磁盘上的版本资源,不加载
目标进程。80 个窗口读一遍 ~18ms,而且按路径缓存 —— 列表 1.5 秒重建一次,
不缓存会明显拖慢枚举。

四层顺序:**进程名精确 → 前缀 → 窗口类名/样式 → 文件说明**。

<a id="s18"></a>

## 三个静音开关,只能有一条优先级链

用户报:"设置→场景→顺带静音、行为→隐藏时同时静音、主界面「声音」列,
这三个会打架。"

不是实现错,是**模型错**。当时场景的静音是个 bool,判定写成:

```python
want_mute = (not keep_audio) and bool(profile.mute or mute_on_hide)
```

`or` 意味着场景那个开关**只能加不能减**:全局关掉了、切到场景照样静音,用户
去行为页看开关明明是关的 —— 这就是"打架"。而且 bool 根本表达不了第三种情况:
"这个场景(比如听歌场景)我就是要它响"。

改成两层:

1. **场景静音变三态**:`inherit`(跟随全局)/ `always` / `never`。
2. **判定收敛成一个函数** `should_mute()`,优先级写死:
   声音列(绝对豁免) > 场景三态 > 全局。

以前同一件事写在三个地方(`_hide_one`、`set_audio_policy`、`_apply_profile` 传
`mute=` 参数),而且 `set_audio_policy` 那份还漏了"从不静音"。现在参数链整个
删掉,`hide_pids()` 不再收 `mute=`,只收场景名,由 `should_mute()` 自己查。

配置兼容:`mute_mode` 缺省时读老的 `"mute"` 布尔 —— `true` → `always`,
`false` → `inherit`。**不能**把 `false` 读成 `never`,那样老用户的静音会集体
失效。

最后一步是**别让用户靠猜**:`mute_reason()` 返回(会不会静音, 为什么),
「声音」列的悬停提示直接写"现在隐藏它:会静音 / 原因:场景「上班」设了「总是
静音」",场景页底部也跟着全局开关实时变。三个开关的关系一旦看得见,就不再是
"打架",而是"分层"。

<a id="s19"></a>

## 恢复的目标是"用户按下隐藏那一刻",不是"最后一次补刀那一刻"

用户报:"浏览器/微信本来是最大化的,隐藏之后**有概率**掉成普通窗口。"

隐藏和恢复本身没问题 —— 单次 `hide_window` → `restore_window` 循环跑 15 次,
`IsZoomed` 一次都没丢。问题出在**看门狗**:

```python
# _rehide():目标程序自己把窗口弹出来了,再藏一次
rec = hp.records.get(hwnd)
if rec is None:
    ...
else:
    rec.show_cmd = show_cmd      # ← 用"补刀那一刻"的状态覆盖了恢复目标
```

补刀时机完全不受我们控制,而它记录的那一瞬往往**不是**用户原来的状态:

- 程序自己把窗口弹出来(Chromium 恢复会话、微信被消息唤起)时,它是
  `SW_SHOWNORMAL` —— 覆盖之后,"最大化"就永久降级成普通窗口;
- 如果补刀时窗口还藏着(`_watch` 选目标与 `_rehide` 执行之间有间隔),
  `hide_window` 读到的可能是 `SW_HIDE`,而 `restore_window` 又会把
  `SW_HIDE` 映射成 `SW_SHOWNORMAL` —— 一样是小窗口;
- 顺带把 `ex_style` 也覆盖了:那会儿我们刚加过 `WS_EX_TOOLWINDOW`,
  记成"原始样式"就等于恢复时永远去不掉,窗口回来了却不在任务栏/Alt+Tab 里
  (实测补刀后读到 `ex=0x00000180`,比原始值多了 0x80)。

所以规则是:**`records` 里存的是"用户按下隐藏那一刻"的状态,补刀只负责把
窗口再藏回去,不许改写恢复目标。** 没有记录时才补一条。

第二层保险:`get_window_placement_cmd()` 用 `IsZoomed` 校正 showCmd ——
自绘标题栏 / 伪最大化的程序(Chromium 系、部分 Qt)会给出 `SW_SHOWNORMAL`
却把窗口铺满屏幕。恢复之后再校验一次(`_ensure_maximized`),记录说该最大化
却没最大化就补一刀 `ShowWindowAsync(SW_SHOWMAXIMIZED)`,不指望"一次就对"。

回归:`tests/maximize_test.py` 直接把"误补刀"造出来(窗口藏着时再调一次
`_rehide`;以及先把窗口还原成普通大小再补刀),断言记录不被改写、恢复后
`IsZoomed` 为真、`rect` 与隐藏前完全一致。在修复前的代码上这一步必挂,
实测恢复出来是 `(104,104,584,424)` 的小窗。

## 鼠标侧键:为什么必须用低级钩子,以及为什么要"吃掉"它

用户的原话是:"我正好手上一只握着鼠标,那我就直接用鼠标侧键;手放在键盘上,
就按键盘快捷键。" —— 这不是二选一,是**两个都要同时生效**。

### 为什么不能用 RegisterHotKey

`RegisterHotKey` 的参数是虚拟键码(VK),键盘才有这个概念。鼠标侧键
(XBUTTON1/2)根本不是键盘事件,系统里没有对应的 VK。想接管只有两条路:

- **Raw Input**:建一个隐藏窗口收 `WM_INPUT`,还得 `RIDEV_INPUTSINK` 抢全局。
  要处理设备枚举、报文解析,而且**没法决定"要不要把事件继续传下去"** ——
  浏览器照样会收到,你只是在旁边偷听。
- **`WH_MOUSE_LL` 低级钩子**:回调里直接决定 `return 1`(吃掉)还是
  `CallNextHookEx`(放行)。

选后者,因为"能不能吃掉"是关键需求(见下)。

### 为什么要吃掉:不然恢复后网页已经不是原来那页了

侧键在浏览器里默认是**后退/前进**。如果只监听不拦截,用户按一下会同时发生
两件事:窗口藏起来了,页面也翻页了。等他恢复回来,看到的是上一页 —— 而手忙
脚乱的时候没人记得自己刚才看到哪。所以**匹配到已配置的侧键就必须吃掉**。

代价是那个键在浏览器里永久失效。这个代价必须写在界面上,不能让用户自己
发现 —— 设置页那行说明里写明了"设成快捷键的那个侧键,以后在浏览器里不再
前进/后退"。只配一个的话,另一个侧键照常可用。

不加"保留原功能"开关,是因为那等于提供一个必然让人困惑的选项(藏了窗口
但页面也变了,两者不可兼得,不如不给)。

### 钩子会吃掉自己的输入

设了侧键 A 之后想改成 B,点进录入框按 B —— **没反应**。因为钩子此刻正在拦
截所有匹配的侧键,而它不知道"用户正在设置"。B 没在配置里所以放行,但 A
已经被自己的钩子吃了,你连"取消"都按不了。

解法是一个全局的**捕获态**(`threading.Event`):界面点进录入框时置位,钩子
看到它就把侧键**放行**并转发给界面,而不是触发动作。这也顺便让"把侧键从
A 改回 A"变得可行。

### 捕获不能靠 Qt 的鼠标事件

第一版想在 `QPushButton.mousePressEvent` 里读 `Qt.BackButton`。实测
(SendInput 合成 XBUTTON,按钮有焦点)**完全收不到** —— 因为侧键的
`WM_XBUTTONDOWN` 只投递给**光标下的窗口**,而录入时用户的手还在鼠标上,
光标未必停在那个按钮里。

所以捕获也走同一个钩子,通过一个模块级信号总线转给界面。`mousePressEvent`
那条路留着做兜底(光标正好在按钮上时能用),两条路同时到达也不会重复执行 ——
第二次进来时捕获态已经是关的了。

### 两个槽位而不是一个

主界面里每个动作有两格:**左边键盘、右边侧键**。没做成"一个键框,按什么
录什么",因为那会让人分不清"我设的到底是键盘还是鼠标",而且改了一种就得
覆盖另一种。两格各管一种,互不影响;侧键那格按 `Delete` 清空(否则设上了
撤不掉)。

### 副作用与边界

- 装上钩子后**每个鼠标事件**(移动、滚轮、左右键)都会进 Python 回调。
  快路径必须是两个整数比较就 `CallNextHookEx`,否则 1000Hz 的游戏鼠标会
  把回调打满。这是"为了一个侧键,全局装钩子"必须付的代价。
- `HHOOK` 在 64 位下是**指针**,`SetWindowsHookExW.restype` 必须显式声明成
  `c_void_p`;按默认 `int` 接收会被截断,之后 `UnhookWindowsHookEx` 传进去
  是无效句柄 —— 表现为"钩子卸不掉"。测试里专门有一条:停掉热键线程后再按
  侧键,必须**不再触发**。
- 只配了侧键、一个键盘热键都没配时,线程也必须起来(条件从"有任何 vk"
  改成"有任何 vk 或任何侧键"),否则钩子根本不存在。测试第 3 组就是这个。

<a id="s21"></a>

## 静音不能按整棵进程树来 —— explorer 是所有程序的爹

用户报了一个"逆天 bug":勾一个 D 盘的文件资源管理器窗口,隐藏它,**正在放视频
的浏览器突然没声了**,而且连别的程序一起哑。诡异之处在于:只有先把浏览器那行的
「声音」列勾上(= 藏了继续响),再藏文件夹,才会暴露 —— 因为不勾的话浏览器本来
就该被静音,用户根本不会注意到。

### 根因:进程树在这个场景里是错的

`set_process_mute()` 一直用的是"目标 pid + **全部**子孙",理由很正当:Chromium
系把音频放在 audio service 子进程里,只按主窗口 pid 找会话什么都静不了。

但 `explorer.exe` 是**桌面所有程序的父进程**。实测这台机器上:

```
pid 14060 (explorer.exe) 的子孙共 83 个,涉及 21 种映像
    msedge.exe   x19      cef_server.exe x15   conhost.exe x15
    workbuddy.exe x9      bash.exe x4         node.exe x4
```

于是"静音一个文件夹" = "静音桌面上所有正在出声的程序"。而「声音」列的豁免是
按**进程名**判的,只作用于"正在被隐藏的那个程序"(explorer),管不到被进程树
连带进去的浏览器 —— 两个范围不一致,豁免就形同虚设。

### 修法:只认**同名**子孙

```python
process_descendants(pid, same_name=True)   # 只保留映像名与目标相同的
```

Chromium 的多进程模型下,所有子进程的**映像名和主进程完全一样**(都是
`msedge.exe`,只是命令行参数不同)。所以"同名"既能覆盖"音频在子进程"这个
原始需求,又天然不会牵到 explorer 名下的其它程序 —— 它们的名字都不同。

实测对比(同一台机器、浏览器正在播放):

| | 静音范围 | 范围内的音频会话 |
|---|---|---|
| 修复前 | 83 个进程 | WorkBuddy + 浏览器(都被掐) |
| 修复后 | 1 个(explorer 自己) | 无 |
| 藏 Edge 时 | 主进程 + 同名的 19 个子进程 | 音频子进程正常覆盖 |

### 取舍

- **少静音**比**误静音**安全。如果某个程序把音频放在**不同名**的子进程里,
  现在会静音失败(它继续响)——这比"藏个文件夹把全桌面静音"好得多。
- 不同名的子进程仍然会被**遍历**(可能有同名的孙进程),只是不计入范围。
- 顺带更精确了:两个不同 profile 的浏览器是不同进程,藏 A 不再静音 B。

回归:`tests/audio_scope_test.py` 用真实进程树验证三件事 —— 自建树里同名留、
不同名丢;explorer 的静音范围只剩它自己且不含任何发声进程;浏览器的音频子进程
仍被覆盖。最后真调一次 `set_process_mute(explorer)` 断言**返回 0**(修复前是 2),
并当场取消静音兜底。
